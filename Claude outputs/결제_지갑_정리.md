# 결제 / 지갑

찐막 프로젝트 – 결제 및 지갑 도메인

---

## 1. 담당 도메인

### Payment (결제 도메인)

토스페이먼츠 연동을 통한 예치금 충전·주문 결제 승인과, 실패·미완료 건의 복구 담당

**주요 구현 기능**

- 예치금 충전 요청·승인·취소 (토스페이먼츠 일반 결제 API)
- 주문 결제 요청·승인 (전액 예치금 / 부족분만 PG 충전 후 결제)
- 결제 전 견적, 결제·충전 내역 조회
- 주문 그룹 삭제(결제 기한 만료) 이벤트 수신 → 미완료 결제 종료
- 미완료 충전 복구 스케줄러

### Wallet (지갑 도메인)

예치금·정산금 보관, 주문 대금 에스크로 홀딩, 모든 잔액 변동의 원장 기록 담당

**주요 구현 기능**

- 회원 생성 이벤트 수신 → 지갑 생성
- 예치금·정산금 잔액 조회
- 주문 대금 홀딩 → 구매 확정 → 정산 / 환불
- Append-only 원장(WalletTransaction) 기록·조회
- 홀딩 조회 (구매자: 묶인 돈 / 판매자: 정산 예정 금액)
- 예치금 전액 출금(명목상), 정산 정보 조회 포트

## 2. 트러블슈팅

### 2.1. 결제·지갑을 나눴더니 경계 비용이 도메인 비용보다 커짐

**상황**

- 처음에는 결제(PG 연동)와 지갑(잔액·원장)을 별도 컨텍스트로 설계
- 결제 1건마다 "잔액 조회 포트 → PG 승인 → 충전 이벤트 → 지갑 반영 → 완료 이벤트 회신 → Payment 상태 닫기"의 왕복이 필요

**원인**

- 충전 이벤트가 유실되면 돈은 들어왔는데 지갑에 반영이 안 되므로, Payment 상태를 아웃박스처럼 쓰는 재발행 스케줄러·회신 이벤트·포트 멱등키까지 전부 필요해짐
- 그런데 주문 결제는 항상 지갑 잔액을 움직이는 일이고, 충전은 결제에서만 들어옴 → 이 복잡도는 도메인이 아니라 **경계 때문에** 생긴 것

**해결**

- 두 컨텍스트를 `payment` 하나로 병합 (#131)
- 진입점만 역할별로 분리: `PaymentFacade`(토스 호출이 끼는 흐름), `WalletFacade`(이벤트로 들어오는 지갑 작업)
- 충전 입금 + 예치금 차감 + 홀딩 생성이 한 트랜잭션

**결과**

- 충전 이벤트·회신 이벤트·아웃박스 스케줄러·`WalletPort` 삭제
- "충전은 됐는데 홀딩이 안 된" 중간 상태가 DB에 남을 수 없음

### 2.2. 낙관적 락 재시도가 동작하지 않음

**상황**

- 사용자 지갑은 `@Version` 낙관적 락. 동시 결제·충전 시 `OptimisticLockingFailureException`이 났고, 재시도 로직을 넣었는데도 계속 실패

**원인**

- 낙관적 락 충돌은 **커밋 시점**(flush)에 발생. `@Transactional` 메서드 안에서 catch해 재시도하면 같은 트랜잭션·같은 영속성 컨텍스트 안이라 의미가 없음

**해결**

- 재시도를 트랜잭션 바깥으로 이동: `WalletRetrySupport`를 컨트롤러·포트 어댑터(`in/`)에서 파사드 호출 전체를 감싸도록 배치 (#94, #96)
- 재실행되는 유스케이스가 모두 멱등하도록 설계 (orderGroupId 멱등키, 토스 `Idempotency-Key`, `ALREADY_PROCESSED_PAYMENT` 처리)

**결과**

- 최대 3회 재시도 후 `WALLET501`로 사용자에게 안내
- "재시도 = 트랜잭션 통째로 다시"라는 규칙이 파사드/어댑터 계층 분리의 근거가 됨

### 2.3. ESCROW 지갑 핫스팟과 데드락

**상황**

- 모든 결제·환불·정산이 ESCROW 시스템 지갑을 거침. 낙관적 락으로 두면 동시 결제가 많을수록 충돌·재시도가 폭증
- 구매자 지갑과 ESCROW를 다른 순서로 잡는 유스케이스가 생기면 데드락 가능

**해결**

- 시스템 지갑(ESCROW/FEE)은 `SELECT ... FOR UPDATE` 비관적 락 + 3초 타임아웃 (`SystemWalletFinder.escrowForUpdate`)
- 락 획득 순서를 `USER → ESCROW → FEE`로 모든 유스케이스에 고정하고 주석으로 명시
- 읽기만 할 때는 락 없는 `escrow()` 사용

**결과**

- 사용자 지갑은 충돌 시에만 비용, 시스템 지갑은 짧게 직렬화
- 홀딩·환불·정산 유스케이스가 같은 순서로 락을 잡아 데드락 경로 제거

### 2.4. 잔액은 바뀌었는데 원장이 없는 상태

**상황**

- 초기에는 유스케이스마다 `wallet.deposit()` 뒤에 `WalletTransaction`을 따로 저장. 한쪽만 호출하거나 금액 부호를 잘못 넣는 실수가 반복

**해결**

- `LedgerRecorder` 지원 컴포넌트로 추출 (#110): 잔액 변경과 원장 기록을 한 메서드에서 수행 (`transfer`, `transferToSettlement`, `deposit`, `withdraw`)
- 원장은 append-only, 부호 있는 금액 + `balanceAfter` 스냅샷, 쌍 기록은 같은 `transactionGroupId`, 멱등키 `refType:refId:type` 유니크

**결과**

- 불변식을 코드로 표현 가능: 그룹 합 0, `HELD` 홀딩 합 == ESCROW 잔액
- 잘못된 기록은 수정 대신 `REVERSAL` 역기록으로만 정정

### 2.5. 토스 승인 실패 사유가 롤백에 휩쓸려 사라짐

**상황**

- 승인 실패(카드 한도 초과 등) 시 `Charge`를 `ABORTED`로 바꾸고 토스 code/message를 남기려 했으나, 예외로 파사드 트랜잭션이 롤백되면서 기록도 같이 사라짐

**해결**

- `ChargeFailureRecorder`를 `REQUIRES_NEW`로 분리해 바깥 롤백과 무관하게 사유 저장
- 주의점 발견: 바깥 트랜잭션이 이미 같은 `Charge` 행을 수정(flush)한 뒤면 행 락 때문에 새 트랜잭션이 대기하다 실패 → 승인 **전** 시점에만 호출하도록 제한하고, 그 외 케이스는 복구 스케줄러에 맡김
- `PgApiException`에 토스 code/message 보존

**결과**

- 충전 상세 조회에서 실패 사유 확인 가능, 프론트 안내 문구에 활용

### 2.6. 토스는 승인됐는데 우리 DB 반영이 실패

**상황**

- 토스 승인 성공 후 지갑 입금·홀딩 중 예외(낙관적 락 충돌, 잔액 불변식 위반 등)가 나면 사용자 카드는 결제됐는데 예치금은 없는 상태

**해결**

- 승인 이후 구간을 `try/catch`로 감싸 실패 시 `PgApprovalSupport.cancelApproved`로 토스 결제 취소(보상) 후 예외를 올려 롤백
- 취소마저 실패하면 로그만 남기고, `Charge`는 `REQUESTED`로 남으므로 복구 스케줄러가 토스 상태(CANCELED)를 보고 `ABORTED`로 닫음
- 승인 응답도 검증: `status=DONE`, `orderId`, `totalAmount`가 요청과 다르면 취소 후 `PG_NOT_APPROVED`

**결과**

- 돈만 빠져나가는 경로 차단. 실패 시 `Payment`는 `CHARGING`에 남아 "다시 결제하기"가 가능

### 2.7. 결제창을 닫은 충전 건이 영원히 REQUESTED

**상황**

- 결제창에서 이탈하거나 승인 응답 전 네트워크 오류가 나면 `Charge`가 `REQUESTED`에 머묾. 토스 쪽은 승인됐을 수도, 아닐 수도 있음

**해결**

- `PaymentScheduler`(10분 주기)가 40분 이상 `REQUESTED`인 건을 `pgOrderId`로 토스 조회 (토스 인증 유효 시간 10~30분보다 넉넉히)
  - `DONE` + 수동 충전 → 지갑 반영 후 `CHARGED` (사용자 돈 보존)
  - `DONE` + 주문 충전 → 주문 흐름은 깨졌으므로 토스 취소 후 `ABORTED`
  - 그 외 → `ABORTED`
- 건마다 별도 트랜잭션, 네트워크 오류는 다음 주기 재시도
- `pgOrderId`를 승인 전 복구 조회 키로 쓰기 위해 서버가 생성(`CHG-` + UUID)

**결과**

- 상태 머신 `REQUESTED → CHARGED → USED / CANCELED / ABORTED`에서 빠져나갈 수 없는 상태 제거

### 2.8. 새로고침·재시도로 승인 요청이 중복 도착

**상황**

- successUrl 페이지 새로고침, 프론트 재시도, 낙관적 락 재실행 등으로 같은 confirm이 여러 번 들어옴

**해결**

- 토스 호출에 `Idempotency-Key`(`charge-confirm-{id}`, `charge-cancel-{id}`)
- 토스가 `ALREADY_PROCESSED_PAYMENT`를 돌려주면 승인 대신 `paymentKey` 조회로 대체
- 이미 `PAID`/`CHARGED`면 아무것도 하지 않고 결과만 반환 (`PaymentPaidEvent`도 재발행하지 않음)
- 원장 멱등키 유니크 제약이 마지막 안전망

**결과**

- 승인·취소·요청 API 모두 멱등. 프론트는 `PG004`(통신 불가) 시 안심하고 재호출 가능

### 2.9. 주문 ↔ 결제 통신 방식을 세 번 바꿈

**상황**

- 1차: 주문 생성 이벤트 → 결제 처리 → 완료 이벤트 (이벤트만)
- 2차: 주문이 `PaymentPort` 동기 호출, 반환값으로 주문 완료 처리, 승인 API도 주문 컨텍스트에 둠
- 주문 팀 의견: 승인 API가 주문에 있으면 `pgOrderId`, `paymentKey` 같은 PG 파라미터가 주문 API에 노출되고 토스 변경이 주문에 전파됨

**원인**

- "환불·정산만 이벤트"라는 팀 규칙이 있다고 생각했으나 실제로는 없었음. 나중에 컨텍스트가 완전히 분리된다는 전제로 다시 판단

**해결 (최종)**

- 결제 **요청**은 동기 포트 (주문이 항목·금액을 알고 있고, `NEEDS_CHARGE`면 결제창 파라미터를 바로 받아야 함). 주문은 반환값을 해석하지 않고 클라이언트에 전달
- 결제 **승인**은 결제 API(`POST /api/v1/payments/confirm`)가 직접 수신. `pgOrderId → Charge → Payment`로 찾고 소유자 검증
- 결제 **완료 통지**는 `PaymentPaidEvent` 하나 (전액 예치금 결제와 결제창 승인 모두 같은 이벤트)
- 실패 이벤트는 두지 않음 (승인 실패는 API 에러 응답, 주문은 "결제 대기" 유지)

**결과**

- 결제창 파라미터의 주인이 결제 컨텍스트로 통일
- 주문이 `PAID`가 되는 경로가 이벤트 하나 → 분리 후 Kafka 토픽 하나로 치환 가능

### 2.10. 부족분 자동 충전 수단 선택: 빌링키 vs 브랜드페이 vs 일반 결제

**상황**

- 네이버페이처럼 "예치금 부족분만 자동 결제해 주문 한 번에 완료"가 목표. 처음엔 빌링키(자동 결제)를 검토

**원인**

- 빌링키는 결제수단 하나에 묶여 그 수단의 한도가 부족하면 주문 전체 실패 → 정기 결제엔 맞지만 금액이 매번 다른 상품 주문엔 부적합
- 브랜드페이(등록 수단 중 선택)는 OAuth Access Token 발급 계층이 커서 1차 범위 초과

**해결**

- 토스 일반 결제(결제위젯) + confirm 방식으로 시작. 사용 API를 승인·취소·조회 2종·거래 조회 다섯 개로 제한
- 가상계좌는 입금 대기 상태·웹훅이 필요해 1차에서 제외 (카드·간편결제만)

### 2.11. 판매 대금이 예치금에 섞임

**상황**

- 정산된 판매 대금이 구매자용 예치금(`balance`)에 들어가면 구매에 쓰이고, 충전 취소 가능 금액 계산에도 섞임

**해결**

- `Wallet.settlementBalance` 분리 (#169), 원장에 `WalletAccount(DEPOSIT/SETTLEMENT)` 컬럼, `balanceAfter`는 주머니별
- `LedgerRecorder.transferToSettlement`로 ESCROW 예치금 → 판매자 정산금 전용 이동
- 정산금 → 예치금 전환은 의도적으로 미지원 (계좌 송금 전까지 보관)

### 2.12. 충전 취소 모델: "남은 잔액 환불" vs "충전 건별 취소"

**상황**

- 잔액만 저장하면 어떤 충전이 쓰였는지 알 수 없어 "실수로 5만 원 충전했는데 취소하고 싶다"를 처리할 수 없음. 토스 부분 취소를 쓰면 환불·재결제가 얽힘

**해결**

- 충전 건 단위 선입선출 (#170): `Charge.remainingAmount`, `DepositConsumer`가 차감 직전에 ① 이 결제용 충전 → ② 환불금 풀 → ③ 오래된 충전 순으로 소비
- 취소는 `remainingAmount == amount`(한 푼도 안 쓰임)일 때 전액만. 일부라도 쓰이면 환불이 돌아와도 영구 취소 불가
- 취소 순서: 지갑 차감 → 토스 취소 → `CANCELED`. 토스 실패 시 롤백으로 차감도 복구되어 별도 보상 불필요

**결과**

- 불변식 `예치금 == 환불금 풀 + Σ충전 잔여금`을 유지하면서 개별 취소 지원
- 환불금을 먼저 쓰게 해 취소 가능 범위 최대화

### 2.13. 결제 기한이 지난 주문이 삭제되면 Payment는?

**상황**

- 주문 팀이 미결제 `WAITING` 주문 그룹을 1시간 뒤 스케줄러로 삭제. 결제 쪽 `Payment`는 `PENDING/CHARGING`에 남고, 사용자가 뒤늦게 결제창을 완료하면 삭제된 주문에 돈이 들어갈 수 있음

**해결 (주문 팀과 합의, #211)**

- 주문이 `OrderGroupDeletedEvent` 발행 → 결제가 `Payment`를 `FAILED`(사유 기록)로 닫고 `REQUESTED` 충전을 `ABORTED`로
- `Payment`는 삭제하지 않음 (돈 흐름 기록이므로 보존)
- 이후 늦은 승인은 토스 호출 전에 `INVALID_PAYMENT_STATUS`로 거절 → 돈이 움직이지 않고 토스 인증은 만료
- 이미 `PAID`인 그룹이 삭제되면 로그만 남기고 주문이 환불 흐름으로 처리

### 2.14. 결제 실패를 프론트가 어떻게 분기할지

**상황**

- 토스 실패, 상태 오류, 잔액 부족 등 실패 종류가 많은데 프론트는 "다시 결제하기"를 보여줄지 "안내 후 이동"할지 알 수 없음

**해결**

- `PaymentErrorCode`에 `retryable` 속성 (PG001~005, CHARGE004 = true)
- `PaymentExceptionHandler`를 결제·지갑 컨트롤러에만 적용(`assignableTypes`)해 공통 `ErrorResponse`의 상위 호환 형태로 `retryable`, `pgCode`, `pgMessage` 추가
- `PG004`(통신 불가)는 결과 불명이므로 승인 API를 몇 번 재호출(멱등)한 뒤 "주문 내역에서 확인" 안내

## 3. 부족한 점 (현재 한계)

### 3.1. 정산 지급 요청 이벤트 미구독

- 정산 컨텍스트는 `SettlementRequestedEvent`를 발행하지만 결제 쪽에 리스너가 없어 `releaseHolding` 호출 경로가 없음
- 지급 실패 회신 이벤트 미정의 (성공 회신 `WalletReleasedEvent`만 존재)

### 3.2. 이벤트 유실 대비 없음

- Spring `ApplicationEvent` 인메모리 → `AFTER_COMMIT` 리스너 실패 시 유실. `PaymentPaidEvent` 유실 시 돈은 빠졌는데 주문은 미결제
- Outbox·재발행 없음 (2.1에서 걷어낸 뒤 Kafka 도입으로 해결하기로 보류)

### 3.3. 토스 HTTP 호출이 DB 트랜잭션 안

- 파사드 트랜잭션 안에서 승인·취소 호출 → HTTP 대기(최대 60초) 동안 DB 커넥션·지갑 락 점유. 1차에서는 비용 감수

### 3.4. 대사(Reconciliation) 미구현

- `findTransactions`(토스 거래 조회) 클라이언트만 준비, 배치 없음
- 원장 불변식(그룹 합 0, HELD 합 == ESCROW, 예치금 == 환불금 + Σ잔여금) 검증 배치 없음

### 3.5. 스케줄러 다중 인스턴스 미고려

- `PaymentScheduler`가 인스턴스마다 실행 (분산 락 없음)

### 3.6. 출금·계좌가 명목상

- 실제 송금 없음, 정산금 출금·`BankAccount` 미구현, `Withdrawal.FAILED` 경로 미사용

### 3.7. 지갑 상태 미적용

- `WalletStatus(ACTIVE/FROZEN/CLOSED)` 정의만 있고 `Wallet`에 연결되지 않음

### 3.8. 토스 웹훅 미수신

- 승인 완료를 클라이언트 confirm에만 의존 → 이탈 시 40분 뒤 복구까지 대기

### 3.9. 환불·정정 범위

- 전액 환불만, `REVERSAL` 정정 API·절차 없음

### 3.10. 테스트

- 유스케이스·API 테스트(약 60개)는 있으나 동시성·토스 장애 시나리오 통합 테스트 부족

## 4. 고도화 계획 — Kafka 전환과 MSA 분리

최종에는 모놀리스가 아니라 컨텍스트별로 서버를 따로 띄우는 MSA로 간다. 결제·지갑은 `payment-service`로 독립 배포하고, 이벤트는 Kafka, 동기 호출은 REST로 치환한다. 지금까지 "분리를 전제로" 잡아 둔 결정(FK 없음, `WalletMember` 로컬 복제, 포트 인터페이스, 이벤트 하나로 완료 통지, 같은 트랜잭션 리스너에 기대지 않음)이 그대로 쓰인다.

### 4.1. 서비스 분리 구조

- `payment-service`: `boundedContext/payment` + 자체 DB(`wallet`, `charge`, `payment`, `holding`, `wallet_transactions`, `withdrawal`). 다른 서비스 테이블 접근 없음
- 동기 호출 치환
  - 주문 → 결제 `PaymentPort.requestPayment` → 주문 서비스 안의 REST 클라이언트 구현체 (`PaymentPortAdapter` 자리에 들어감). 응답 계약은 지금의 `PaymentResultDto` 그대로
  - 정산 → 결제 `findSettlementOf` → REST (또는 `WalletReleasedEvent`에 금액을 실어 조회 자체를 없앰)
  - 타임아웃·재시도: 주문은 요청이 멱등(orderGroupId)이므로 타임아웃 시 재호출, 결제 응답 유실 시 `PaymentPaidEvent`로 수렴
- 인증: 게이트웨이가 JWT 검증 후 `memberId`를 헤더로 전파. `AuthPrincipal` 추출 로직만 헤더 기반으로 교체
- 회원 데이터: `MemberCreatedEvent`를 Kafka로 받아 `WalletMember` 복제 (현재 구조 유지). 결제 서비스는 회원 DB를 모름

### 4.2. Kafka 이벤트 설계

**발행 토픽 (payment-service → 외부)**

| 토픽 | 이벤트 | 파티션 키 | 소비자 |
|---|---|---|---|
| `payment.paid` | PaymentPaidEvent | orderGroupId | order |
| `wallet.refunded` | WalletRefundedEvent | orderId | refund |
| `wallet.released` | WalletReleasedEvent | orderId | settlement |
| `wallet.release-failed` | WalletReleaseFailedEvent (신규) | orderId | settlement |
| `wallet.member-created` | WalletMemberCreatedEvent | memberId | (내부) |

**구독 토픽 (외부 → payment-service)**

| 토픽 | 이벤트 | 처리 |
|---|---|---|
| `member.created` | MemberCreatedEvent | WalletMember 복제 → 지갑 생성 |
| `refund.accepted` | RefundAcceptedEvent | 홀딩 REFUNDED, ESCROW → 구매자 |
| `order.confirmed` | OrderConfirmPurchaseEvent | 홀딩 CONFIRMED |
| `order-group.deleted` | OrderGroupDeletedEvent | Payment FAILED, 충전 ABORTED |
| `settlement.requested` | SettlementRequestedEvent | 홀딩 RELEASED, ESCROW → 판매자 정산금 + FEE (3.1 해결) |

**신뢰성**

- **Outbox 패턴**: 이벤트를 비즈니스 트랜잭션과 같은 DB 트랜잭션에서 `outbox` 테이블에 저장 → 별도 퍼블리셔(폴링 또는 Debezium CDC)가 Kafka로 발행 후 마킹. 2.1에서 걷어낸 아웃박스를 이번엔 "이벤트 저장소"로만 쓰고 재발행 로직은 퍼블리셔 하나로 통일
- **멱등 컨슈머**: 모든 이벤트에 `eventId`(이미 `PaymentPaidEvent`에 있음). `processed_event(eventId)` 테이블에 기록하며 처리, 중복은 무시. 지금의 "이미 PAID/REFUNDED면 아무것도 안 함" 상태 분기는 2차 안전망으로 유지
- **순서 보장**: 같은 주문 그룹·주문의 이벤트가 같은 파티션에 가도록 키 고정. 지갑 단위 순서가 필요한 곳(같은 지갑에 환불·정산이 동시)은 낙관적 락 재시도로 흡수
- **재시도·DLQ**: 컨슈머 실패는 지수 백오프 재시도 후 `*.dlq` 토픽으로. 결제처럼 돈이 걸린 이벤트는 DLQ 적재 시 알림, 운영자가 재처리
- **스키마**: 이벤트 DTO를 `shared/payment/event`에서 별도 계약 모듈(또는 Avro/JSON Schema + 스키마 레지스트리)로 분리해 서비스 간 버전 관리

### 4.3. MSA에서 달라지는 트랜잭션 경계 (사가)

- 지금은 "주문 요청 → 결제 포트 → PAID" 가 한 JVM. 분리 후 주문 서비스가 결제 응답을 받고 자기 DB 반영에 실패하면 **결제는 PAID, 주문은 대기**인 불일치가 생김
  - 대응: 주문은 `PaymentPaidEvent` 컨슈머에서 "그룹이 결제 대기 상태가 아니면 환불 요청"으로 보상 (이미 합의된 규칙), 결제는 멱등 재요청에 `PAID`를 그대로 반환
- 결제 → 지갑 구간은 같은 서비스·같은 DB이므로 사가 불필요 (병합 결정이 MSA에서도 유효)
- 정산 지급: `settlement.requested` 건별 처리, 실패는 `wallet.release-failed`로 회신 → 정산 서비스가 재요청·보류 (정산서 1건 = 홀딩 여러 건이므로 건별 멱등)

### 4.4. 토스 연동 고도화

- 토스 HTTP 호출을 트랜잭션 밖으로: "검증 트랜잭션 → 토스 승인(트랜잭션 없음) → 반영 트랜잭션" 3단계 (`TransactionTemplate`). 보상 취소 로직은 유지, 지갑 락 점유는 DB 작업 시간만큼으로 축소 (3.3)
- 토스 **웹훅** 수신 엔드포인트: `DONE`/`CANCELED` 통지를 받아 복구 스케줄러를 기다리지 않고 즉시 반영, 시크릿 검증 (3.8)
- 브랜드페이 전환(선택): 등록 결제수단 선택 + OAuth 토큰 발급 구현

### 4.5. 운영 안정성

- 스케줄러: 분리 후 `payment-service` 다중 인스턴스 → ShedLock(DB 기반 분산 락) 또는 스케줄러 전용 인스턴스 1대 (3.5)
- 대사 배치 (3.4): 일 1회 토스 `GET /v1/transactions` ↔ `Charge` 비교, 원장 불변식 3종 검증, 위반 시 알림. 운영자용 `REVERSAL` 정정 API(사유 필수)
- `WalletStatus`를 `Wallet`에 적용, 충전·결제·입금 가능 여부를 상태로 검사 (3.7)
- 관측성: 이벤트 헤더에 `traceId` 전파(분산 트레이싱), 결제 성공률·보상 취소 횟수·DLQ 적재 수 메트릭

### 4.6. 테스트 전략

- Testcontainers(Kafka + MySQL)로 발행·구독·멱등 컨슈머 통합 테스트
- WireMock으로 토스 승인 성공 후 DB 실패, 네트워크 타임아웃, `ALREADY_PROCESSED_PAYMENT` 시나리오
- 동시 결제·충전 취소 경합 테스트 (낙관적 락 재시도 소진 → `WALLET501`)
- 주문 ↔ 결제 REST 계약 테스트 (Spring Cloud Contract 또는 OpenAPI 기반)

### 4.7. 선택 과제

- 정산금 출금·`BankAccount` 등록 (송금 대신 기록, `Withdrawal REQUESTED → COMPLETED / FAILED` 활성화)
- 부분 환불 (홀딩 분할 또는 환불 금액 컬럼)
- 가상계좌 결제수단 (입금 대기 상태 + 웹훅 전제)
